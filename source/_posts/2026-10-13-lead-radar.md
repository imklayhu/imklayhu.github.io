先说清楚：这不是一篇「我们用 AI 颠覆获客」的 PPT 文案，是一篇「我把刷评论这件事，拆成一串 n8n 工作流」的施工笔记。官网在这儿：[Lead Radar 落地页](https://imklayhu.github.io/lead-radar-website/)，源码仓库是 [`imklayhu/lead-radar`](https://github.com/imklayhu/lead-radar)（没有 README 大饼，全是 `workflows/`、`scripts/`、`docs/`，干就完了）。

同类的小玩意儿还有 [FatTI](https://fatti.ai-dddd.top)、[DevEase](https://devease.ai-dddd.top)、[训记](https://xunji.ai-dddd.top)——都是「自己先用、再考虑别人能不能用」那挂的。这篇只深挖 Lead Radar。

## 背景动机：私教获客，本质是体力活

故事起因很朴素。假设你是健身自由教练，想在小红书找「想练、想请私教」的人。日常操作大概是：

1. 搜关键词；
2. 点进帖子；
3. 翻评论；
4. 凭感觉判断这人有没有意向；
5. 再琢磨第一句私信怎么写。

能做，但很累。而且「意向」这件事，人眼刷久了也会钝——明明是「求推荐靠谱教练」，你可能当成普通闲聊滑过去了。

所以最初的问题其实就一句话（仓库里 `refs.md` 原话大意）：**用自动化从抖音/小红书评论里识别销售线索，入库，生成首次触达文案，由人工决定要不要发。**

注意最后半句：人审核。不是全自动骚扰机。这个边界从 Day 1 就钉死了。

抖音后来砍了（TikHub 权限与稳定性问题，`03`/`04` 工作流现在只是废弃占位）。当前版本主战场是**小红书**，场景 Prompt 也先锁在**健身私教**。

## 做了什么：一句话发起，六步漏斗交出去

产品侧一句话：**在飞书群里 @Lead Radar，用自然语言发起采集；系统跑完关键词搜索 → 帖子路由 → 评论抓取 → AI 打分 → 人工审核，交付可跟进线索。**

落地页把漏斗写成六步，和仓库实现是对齐的：

1. **关键词搜索**：TikHub 搜小红书笔记；
2. **帖子路由**：LLM 先筛一遍值得下钻的帖（跳过无意义互动帖）；
3. **评论抓取**：对高「评论产出分」的帖批量拉评论（含内嵌子评论，能薅就薅）；
4. **AI 打分**：按画像与购买意图打分，满分 100，**≥70** 算合格线索；
5. **人工审核**：飞书卡片点通过/拒绝；
6. **有效线索**：人审过的才算「能跟进」的交付物。

用户体验尽量「像聊天」：

- 群里说：`@Lead Radar 帮我找徐家汇附近想请私教的人，少抓一点先看看`
- 机器人回确认卡（关键词、城市、上限参数、预计请求规模）
- **只有原请求者**点「开始采集」才进队列
- 采数结束先发「采数完成」摘要；评分和人审是后面异步 worker 干的

加微信当天能跑第一次采集——这是落地页的承诺，也是我自己验收时卡的口径。

定价按「任务数 / 月」（一次任务 = 一轮完整关键词采集），公开档位是体验版 ¥0、基础版 ¥99、专业版 ¥299、团队版 ¥799。体验版每月 3 次、单城市；取消/过期任务不占配额。这些都写在落地页和 `pricing-and-metering` 设计里，不在这儿编故事。

## 关键链路 / 技术点：n8n 当总线，别的各干各的

### 总览

```
飞书群 @bot
  → feishu-callback-bridge（长连接）
  → WF07 解析自然语言 + 配额门控 + 确认卡
  → WF08 点「开始」→ queued
  → WF09 队列工人 CAS 抢任务
  → WF00：01 搜索笔记 → 02 拉评论（采数短跑，status=harvested）
  → 并行 Schedule：
       05b 评论打分 → leads(pending_group)
       06 聚合发卡 → 人审
       10 慢同步到租户飞书 Base
```

### 技术选型（为什么这么拧）

| 层 | 选型 | 一句话理由 |
|----|------|------------|
| 编排 | 本机 Docker **n8n** | 自托管、Webhook、Data Tables、Execute Workflow 全家桶够用 |
| 采集 | **TikHub**（小红书 App V2） | 付费授权 API，比自己上 Puppeteer 稳；抖音权限不够就先不做 |
| AI | 阿里云 DashScope OpenAI 兼容（默认 `deepseek-v3` / 管线文档里也切过 `deepseek-v4-pro`） | Prompt 在 `prompts/`，挂了有启发式 fallback |
| 交互 | 飞书机器人 + 交互卡片 | 教练本来就在飞书里，审核不用再开一个后台 |
| 存储 | **n8n Data Tables 真源** + 飞书多维表慢同步镜像 | 热路径别跟飞书 API 缠死；运营看中文表就行 |

`docker-compose` 里两件套：`n8n` + `feishu-callback-bridge`。飞书长连接**每个应用只能挂一个客户端**，所以 bridge 单独成服务，专门转发 mention / 卡片回调到 n8n webhook。

### 几个我觉得「值钱」的设计

**1. 采数和分析拆开（ingest-first）**

早期 WF09 一把梭：`01→02→05b→06`，执行时间又长又容易 timeout。后来改成：

- 09/00 只负责搜帖 + 拉评论，成功就 `harvested`，释放同群采数锁；
- 05b Schedule（约 1 分钟）扫 `score_status=pending` 批打分；
- 06 Schedule（约 2 分钟）flush 待审卡。

好处很实在：采数失败可重试采数；分析挂了不必重抓 TikHub（钱啊）。同群任务 A `harvested` 后，B 可以接着跑。

**2. Data Tables 是真源，飞书是交付镜像**

热路径（01/02/05b/06/07/08/09/00/11）只读写 DT：`leads` / `notes` / `comments` / `note_task_links` / `collection_tasks` / `tenants` / `coach_profiles`。  
WF10 按 `tenant_id` 慢同步到**每个租户自己的飞书 Base**（模板复制），教练只读 view。飞书表不做手改回写——否则双写地狱，我已经踩过一脚（旧英文 Bitable 切流时还专门要求停掉会双写的遗留 05）。

**3. 自然语言采集 ≠ 让 LLM 随便飞**

WF07 会把自然语言 clamp 成受控配置：`keywords[]`、城市/区域、各种 max 上限。同义词用 `/`、顿号拆开，最多 `COLLECTION_MAX_KEYWORDS`（默认 5），每个词各自 `search_notes`，再按 `note_id` 去重。确认卡展示**全部关键词**，不是偷偷压成一个。

区域闸门：关键词得带城市/区域信号；体验版/基础版还有**服务城市数**限制（城市级归一化，`上海 徐汇` 算 1 城）。

**4. 多租户：群即租户**

客服建群 → 拉机器人 + 教练 → `@Lead Radar 初始化当前租户`（WF14）：按群名前缀解析档位、复制交付 Base、教练只读协作者。套餐变更走 WF13（仅客服），先改群名再落库，避免半更新。

**5. 人审卡片：快 ACK + 异步改卡**

飞书卡片回调最好 3 秒内返回。早期把写表绑在回调响应里，结果 Toast 成功、按钮还在——经典「看起来成功其实没改干净」。后来拆成：先 Toast，再异步更新 DT + 主动改消息卡片为已处理态，并用 `record_id + decision` 做幂等。

**6. 成本意识写进漏斗**

TikHub 按次计费，所以：

- 搜索结果尽量吃满再路由，而不是只取前 1–2 条；
- `coach_supply` 且评论数过低的帖直接跳过拉评；
- 评分有 `COLLECTION_MAX_LLM_CALLS`、新鲜度衰减、过期评论硬跳过；
- 创建任务前按月配额门控（任务数 + LLM 调用），超限不建记录。

设计文档里有一套成本模型（边际/全成本），用来支撑档位定价——那是规格真源，不是营销稿里的「AI 降本 99%」。

## 踩坑与取舍（吐槽时间）

**取舍一：不做自动私信。**  
技术上不是不能接，但合规和产品边界都说「人工审核后才触达」。线索质量再好，批量骚扰也是把自己送进平台黑名单的最快路径。触达文案可以生成（`prompts/outreach-copy-fitness.md`），发不发教练说了算。

**取舍二：抖音先放弃。**  
仓库里还留着 `03`/`04`，但明确废弃。没有权限的 API 调用，不如诚实不做。

**取舍三：真源从飞书迁到 Data Tables。**  
飞书 Bitable 当运营看板很香，当高并发热路径存储就……嗯，慢同步 + 模板复制多租户，比「一切都写飞书」清醒多了。迁移脚本、对账、切流停写旧表，这一套比写业务节点还磨人。

**取舍四：配额校验 fail-open。**  
查配额失败时放行，优先保内测可用性。严格计费上线前，这是有意识的「先能用、后算准」。

**踩坑：飞书权限宇宙。**  
`@机器人` 收不到消息？多半是缺 `im.message.receive_v1` 或没配 `FEISHU_BOT_OPEN_ID`。改群名？机器人还得是群主/管理员，或者群允许改名。长连接不能多开。每一个都是「日志里只有 ws client ready，群里一潭死水」级别的玄学，桥接服务的单测和 `check-feishu-message-scopes.sh` 是血泪换的。

**踩坑：单体工作流太长。**  
n8n runner timeout、执行超时、同群互斥锁捂太久——全是「看起来能跑、 concurrent 一上就翻车」。拆成 harvest / score / flush 三班倒之后，心情都好了。

**踩坑：AI 会误判，所以 ≥70 还要人审。**  
落地页写得很直白：合格线索 ≠ 有效线索。有效 = AI 过线 + 人过目。我宁可少交几条，也不想教练的时间浪费在假意向上。

## 小结

Lead Radar 对我来说，不是「又一个 AI Agent Demo」，而是一条可交付的获客流水线：

- 入口足够懒（飞书一句话）；
- 中间足够抠（付费 API、LLM 预算、去重、配额）；
- 出口足够稳（人审 + 按租户隔离的线索清单）。

它现在已经能给真实私教跑采集；官网、定价、FAQ 都在 [lead-radar-website](https://imklayhu.github.io/lead-radar-website/)。感兴趣就按页上的微信号加我，备注「Lead Radar」——别指望我在博客评论区贴一堆密钥和内网 IP。
